# 🐆 SQUADCRAFT — PATROUILLE SERVAL

## Cahier des charges complet — Version mono-patrouille

---

# 1. OBJECTIF DU PROJET

Créer **SquadCraft**, une application web privée dédiée exclusivement à la **Patrouille du Serval**.

L'application sert de centre de gestion numérique de la patrouille :

* membres ;
* parents ;
* rôles ;
* progression ;
* badges ;
* aspirations ;
* annonces ;
* chat ;
* week-ends ;
* matériel ;
* pharmacie ;
* courses ;
* trésorerie ;
* urgences ;
* gestion complète des accès.

Il n'existe qu'une seule patrouille :

```text
🐆 PATROUILLE DU SERVAL
```

Ne pas créer de système de sélection de patrouille dans la première version.

L'architecture doit cependant rester suffisamment propre pour permettre une évolution future vers plusieurs patrouilles.

Le rôle est déterminé automatiquement depuis la base de données.


# 5. GESTION DES ACCÈS

```text

```

Le CP doit pouvoir :

* créer un compte ;
* attribuer un rôle ;
* définir un prénom ;
* générer ou choisir un code d'accès ;
* modifier un compte ;
* réinitialiser un code ;
* désactiver un compte ;

Les comptes supprimés ne doivent plus pouvoir se connecter.

Prévoir un statut :


# 6. TRANSFERT DE CP

Le changement de CP doit être une fonctionnalité spécifique.

Le CP actuel doit pouvoir :

### Étape 1

Créer le profil du futur CP.

Exemple :

```text
Créer un membre

Prénom : Lucas
Place : SP
Rôle : MEMBRE
```

### Étape 2

Configurer son accès :

```text
Lucas
Code d'accès
[ ******** ]
```

### Étape 3

Préparer le transfert.

Action :

```text
[ Transférer la responsabilité de CP ]
```

### Étape 4

Le système transforme le futur CP en :

```text
role = CP
place = CP
```

### Étape 5

Le nouveau CP possède immédiatement tous les droits de gestion.

### Étape 6

L'ancien CP peut ensuite :

* rester membre ;
* devenir SP ;
* devenir MEMBRE ;
* ou voir son accès supprimé.

IMPORTANT :

Il doit être impossible de supprimer l'ancien CP avant d'avoir désigné un nouveau CP si aucun autre CP n'existe.

Le transfert doit être atomique côté serveur afin d'éviter une patrouille sans CP.

# 18. GESTION DU CHAT PAR LE CP

Le CP possède des droits supplémentaires.

Il peut :

* supprimer un message ;
* modérer un message ;
* supprimer plusieurs messages ;
* nettoyer l'historique.

Ajouter dans les paramètres du chat :

```text
⚙️ Gestion du chat

[ Supprimer ce message ]
[ Vider l'historique ]
```

ATTENTION :

L'action :

```text
Vider l'historique
```

doit demander une confirmation forte.

Exemple :

```text
Voulez-vous vraiment supprimer tout
l'historique du chat ?

Cette action est irréversible.

[ Annuler ] [ Supprimer ]
```

Le CP peut également supprimer **l'ensemble du chat/historique** lorsqu'il le souhaite, mais pas le système de messagerie lui-même.

# 28. SÉCURITÉ

IMPORTANT :

Les permissions ne doivent jamais être uniquement gérées dans React.

Chaque API / Server Action doit vérifier côté serveur :

```text
Utilisateur authentifié ?
↓
Quel rôle ?
↓
A-t-il le droit ?
↓
Ressource autorisée ?
↓
Autoriser / refuser
```

Le CP possède les droits administratifs uniquement parce que :

```text
session.user.role === CP
```

Les membres ne doivent jamais pouvoir s'attribuer eux-mêmes le rôle CP.

# 38. TESTS DE SÉCURITÉ À PRÉVOIR

Tester notamment :

* membre essayant de modifier un autre membre ;
* membre essayant de changer son rôle ;
* SP essayant de créer un CP ;
* parent essayant d'accéder au matériel ;
* utilisateur désactivé essayant de se connecter ;
* ancien CP essayant d'utiliser son ancien accès ;

SquadCraft doit être le **tableau de bord numérique de la Patrouille du Serval**.

Le CP doit pouvoir réellement gérer sa patrouille sans avoir besoin de modifier la base de données manuellement.

Le CP peut :

```text

↓
```

# 40. RÈGLE DE CONCEPTION

Construire d'abord une application fonctionnelle et sécurisée.

Ne pas générer uniquement des maquettes ou des composants fictifs.

Toutes les actions principales doivent être reliées à :

* une vraie base de données ;
* de vraies validations ;
* de vrais contrôles d'accès ;
* de vraies opérations serveur ;
* une vraie persistance des données.

L'interface doit ensuite refléter ces permissions.
